## D1 Record-plugin mechanism

**Decision: a transport-level recording wrapper + a builder-registry patch layer, packaged as a pytest plugin at `conformance/record/` in the Python repo, activated by a pytest flag, keyed by test nodeid.**

### D1.1 Wire seam — hook the transport, not the client
The plugin wraps `httpx.MockTransport` at the *transport* level, NOT `MixpanelAPIClient._ensure_client`. Rationale (recon `wire-seam.md` §5): `upload_to_signed_url` (src/mixpanel_headless/_internal/api_client.py:7632-7638) builds a FRESH `httpx.Client` that bypasses `_ensure_client` but still wraps `self._transport` — a client-level hook would miss the GCS PUT. A transport-level hook also covers all four injectable seams uniformly:

1. `MixpanelAPIClient(_transport=...)` — api_client.py:312/:339, funnel at :444-447 (P1/P2/P3, 40+4+21 files).
2. `ReplaysService(_async_transport=...)` — services/replays.py:156/:331-334 (P4, async; `httpx.MockTransport` satisfies both `BaseTransport` and `AsyncBaseTransport`).
3. `OAuthFlow(http_client=...)` — auth/flow.py:168 (P5).
4. `probe_region(client_factory=...)` — auth/region_probe.py:278 (P6).

**Mechanism**: a `pytest` fixture-free `pytest_runtest_setup`/`teardown` hook monkeypatches `httpx.MockTransport.handle_request` and `handle_async_request` (bound-method wrap via `unittest.mock.patch.object` on the class) to:
- record `(seq, method, url, headers, decoded-body)` of every request BEFORE delegating to the test's real handler;
- record the returned `httpx.Response` (status, headers, body bytes — decoded as JSON when `content-type` is JSON, else base64/text) or the raised exception class name (`httpx.ConnectError` etc. — 9 raise sites in 6 files per recon §2 need a `transport_error` representation);
- stamp each interaction with a monotonically increasing per-test sequence number.

Patching the *class* means P7 raw-httpx uses and handler closures are captured with zero test modification. Streaming responses (`client.stream`, api_client.py:1852/:1864) pass through MockTransport like any other. **Stream capture is a TEE, never a read-ahead**: some handlers return `httpx.Response(200, stream=_IterableByteStream(chunks))` THROUGH MockTransport via a raw `httpx.Client` (test_api_client.py:2795-2843 — these do NOT bypass the transport, correcting an earlier draft claim), and those streams are one-shot; reading the body before iteration would raise `httpx.StreamConsumed` in the test and destroy the chunk boundaries `body_stream` exists to preserve. The recorder wraps the response's `SyncByteStream`/`AsyncByteStream` and records each chunk AS THE CONSUMER YIELDS IT — chunk boundaries recorded verbatim, test behavior unchanged. In-memory `content=` bodies are captured directly (safe).

### D1.2 Entry-point seam — registry-driven wrap (builders AND wire APIs)
The transport hook (D1.1) sees only HTTP; it cannot populate `call.api` / `call.input` / `expect.result`, which the schema requires on every vector and which D7/D12 re-invoke at replay. So the registry (`conformance/record/registry.py`, format in D4) covers **two entry-point classes**, both wrapped the same way (capture `(args, kwargs) → return value | raised exception` at call time):

- **Builder entries** (kind `builder` / `validation-error`): the D4.1 facades + D4.2 module functions. Validation errors are captured **structurally at raise time** — the wrapper serializes `BookmarkValidationError.details["errors"]` (already `to_dict()`-serialized per recon `validation-errors.md`; exceptions.py:1283-1287) and, for returned `list[ValidationError]`, serializes each element's `path`/`code`/`severity` — never by parsing pytest `match=` patterns (R5.4).
- **Wire entries** (kind `wire` / `parse`): EVERY public method of `MixpanelAPIClient`, every public query/CRUD/discovery/replay method of `Workspace`, `ReplaysService` public methods, `OAuthFlow.refresh`, and `probe_region` — enumerated in the registry with `kind="wire_api"` and generated mechanically from the class `__dict__`s at registry-build time (PR-2), then hand-audited. The wrapper records `(api, kwargs-via-codecs, return-or-raise)` AND marks the entry/exit span so transport interactions recorded while the call is on-stack are attributed to it (thread-local span stack). This is the mechanism that emits the wire half of the corpus; without it wire vectors would be reconstructed from recordings — tautological/lossy (e.g. `get_events`' internal `to_date=today` default, api_client.py:2380, must stay a DEFAULT in `call.input`, captured from the caller's actual kwargs, never reverse-engineered from the captured request). State-mutating public methods with no return contract (`set_workspace_id`, `Workspace.use`, …) are registered with `kind="wire_state"` — they never become the measured call of a vector but are recorded as `call.setup[]` entries (D2).

Wrapping happens once per session in `pytest_configure` via `unittest.mock.patch` on the module attribute; class methods (`Workspace.*`, `MixpanelAPIClient.*`) are wrapped on the class.

**Re-entrancy guard (outermost-wins)**: capture is SUPPRESSED while another registry wrapper is on-stack (thread-local depth counter). Without this, module-attribute patching also intercepts same-module bare-name calls and recursion (`bookmark_builders.build_filter_section` → `build_filter_entry` at bookmark_builders.py:202; `build_filter_entry` → itself for compound list filters at :563; function-local self-imports bound at call time), and `Workspace` facade internals — emitting vectors for implementation-detail invocations, inflating counts, and coupling `-N` ordinals to internal call structure (regeneration churn on pure refactors). Only the OUTERMOST test-invoked call emits. Note the asymmetry this removes: workspace.py's static from-imports (workspace.py:70) bind pre-patch originals, so facade-internal calls were never captured anyway — the guard makes the rule uniform instead of accidental.

**Test-local clock-mock detection**: before emitting, the wrapper checks whether the wrapped callable's module clock attribute (`date` / `datetime`) is currently a `unittest.mock` object (tests/unit/test_bookmark_builders.py:54-56 patches `bookmark_builders.date` to a fixed 2025-06-15, shadowing the D1.4 freeze). Such captures are NOT emitted (they would deterministically fail replay under `RECORD_EPOCH`); they are logged under manifest category `test_local_clock` (D10), and the affected contracts (`build_date_range`, `build_time_section` today-fill paths) get hand-authored RECORD_EPOCH vectors in PR-7. Census: that file is the only module-clock-patching test file (grep over tests/), so the blast radius is those date builders only.

### D1.3 Activation & output
- Activation: pytest flag `--mp-record-vectors=<output-dir>` (registered via `pytest_addoption`); OFF by default so the normal suite is unaffected. A flag, not an env var, because the autouse `_clean_mp_env` fixture (tests/conftest.py:143-154) scrubs exactly the 7 `MP_*` vars and we must not add plugin config that races it; a non-`MP_`-prefixed env var `CONFORMANCE_RECORD_DIR` is accepted as a fallback for CI convenience (recon `test-infra-ci.md` confirms only `MP_*` names are scrubbed).
- Invocation baseline: `uv run pytest tests -p conformance.record.plugin --mp-record-vectors=conformance/vectors -o addopts="" -m "not live"` plus the exclusion selector from D10. `-o addopts=""` is required because the repo's `addopts = "-vv ..."` (pyproject.toml:140) pollutes collection parsing.
- Keying: each emitted vector carries `source_test` = the exact pytest nodeid (e.g. `tests/unit/test_api_client.py::TestSegmentation::test_limit_param`); vector `id` derivation in D3.
- Per-CAPTURE classification (not per-test): transport interactions are attributed to the wire entry-point call on-stack when they fired (D1.2 span stack). A test with ≥1 wire entry-point call that fired transport emits ONE `wire` vector (setup/measured model, D2). Test-invoked builder registry calls emit `builder`/`validation-error` vectors REGARDLESS of whether the test also fired the transport — dual-seam tests (build params, then send them) emit BOTH; the builder captures are never silently discarded, and `-N` ordinals disambiguate ids. Transport interactions with NO wire entry-point on-stack (the P7 raw-httpx pattern, e.g. `_iter_jsonl_lines` tests driving a bare `httpx.Client` — test_api_client.py:2795-2843) have no library call to replay: no vector, logged under manifest category `raw_transport_no_entrypoint` (their contract is covered by the D4.2 `_iter_jsonl_lines` authored chunk vectors). Tests that fire neither seam emit nothing and are counted as `no_seam_hit` (this resolves recon risk "per-file collected totals are not per-test wire classification": classification is by observed seam firing, not by file membership).

### D1.4 Clock freezing (determinism)
Record mode installs a frozen clock for the whole run: the plugin monkeypatches `datetime.date.today`, `datetime.datetime.now`, and `time.time` via `freezegun.freeze_time(RECORD_EPOCH)` where `RECORD_EPOCH = "2026-01-15T12:00:00Z"` (an arbitrary fixed instant, stored in the manifest). Rationale (recon §7): `get_events` default `to_date=today` (api_client.py:2380), the 403 fallback `today-90d` asserted exactly (test_api_client.py:830), funnel default 30-day `datetime.now()` windows (api_client.py:2937-2948), `bookmark_builders.build_date_range` `date.today()` (bookmark_builders.py:114), and `user_validators` `date.today()` (user_validators.py:211,217). Tests that compute expectations from `datetime.now()` at test time (test_api_client_bookmarks.py:409-410) stay green because test and src see the same frozen clock. The TS runner replays with the same `RECORD_EPOCH` injected into its clock shim (D12). `freezegun` is added to the dev extras (D17).
- UUID normalization: `transform_event` calls `uuid.uuid4()` when `$insert_id` is missing (transforms.py:71). Record mode patches `uuid.uuid4` to a deterministic counter-seeded UUID stream reset per test (`00000000-0000-4000-8000-{seq:012d}`), recorded as-is in vectors; the TS runner injects the same generator.
- Retry jitter: `random.uniform(0, delay*0.1)` (api_client.py:678) affects only sleep durations, never payloads; vectors capture request sequences, not wall time — no patching needed for jitter itself.
- **`time.sleep` policy — VIRTUAL SLEEP, not plain no-op**: record mode patches `time.sleep(d)` to advance the frozen clock by `d` (freezegun `tick(d)`) and return immediately. Monotonic policy is explicit: freezegun freezes `time.monotonic`/`perf_counter` too, and `tick` advances them. This keeps the run fast AND keeps wall-clock-deadline loops deterministic — the lookup-table poll loop (`deadline = time.monotonic() + max_poll_seconds; while time.monotonic() < deadline: time.sleep(poll_interval)`, workspace.py:7857-7860, exercised by the always-PENDING timeout test at tests/unit/test_workspace_data_governance.py:1546-1595 with `max_poll_seconds=0.05`) terminates after a machine-independent, deterministic number of iterations. A plain no-op sleep under a frozen monotonic clock would loop forever; an unfrozen monotonic clock would busy-spin a machine-speed-dependent number of polls, breaking the D8 byte-diff. Verified empirically on the PR-2 pilot subset BEFORE full extraction (explicit PR-2 done-criterion). Both replay runners install the same virtual-sleep shim (D7/D12) so no-Retry-After exponential-backoff vectors (test_api_client.py:459-470 family) replay instantly.

## D2 Vector granularity & multi-request policy

**Decision: one WIRE vector per test, with an ordered `interactions[]` array AND a `call.setup[]` array for multi-CALL tests. Multi-request families are IN scope for Layer 1 — the schema is extended rather than deferring them to Layer 3 — except three explicitly excluded sub-families listed below.**

**Multi-CALL tests (distinct from multi-request)**: many wire tests invoke SEVERAL library entry points — measured: 38 tests in test_api_client*/test_workspace* call ≥2 distinct client/ws methods (e.g. `set_workspace_id` then `activity_feed`), and tests/integration/test_cross_project_iteration.py:157-180 makes 7 entry-point calls (`projects()` + 3× `use(project=)` + 3× `events()`) whose CONTRACT (exactly one `/me` across the whole sequence) spans calls. A single `call.api` cannot represent these, and replaying only one call against the full interaction list would fail on unmutated src, poisoning the D9 control run. Model:
- The **measured call** = the LAST wire entry-point call in the test; its kwargs are `call.input`, its return/raise is `expect.result`/`expect.error`.
- Every EARLIER entry-point call (including `wire_state` entries like `set_workspace_id` / `Workspace.use` — this is also how client-attribute state such as `self._workspace_id`, api_client.py:1418, is reproduced at replay: by re-executing the same public state-mutating call, never by snapshotting private attributes) becomes an ordered `call.setup[]` entry `{api, input}`.
- `expect.interactions[]` contains ALL transport interactions across setup + measured calls, in order; replay executes setup entries then the measured call against the same `VectorTransport`, so extra/missing interactions anywhere in the sequence (e.g. a spurious `/me` re-fetch) fail the vector.
- Known, accepted limitation (logged here, not hidden): setup calls' RETURN VALUES are not diffed — their request sides are fully diffed via `interactions[]`, and any setup call whose return the test itself asserts is still covered on the request/response path. The manifest counts vectors with non-empty `setup` (`counts.with_setup`) so the coverage shape is auditable.

Rationale:
- Plan Appendix A sketches a single `expect.request` / `expect.given_response`; recon `wire-seam.md` §4 measures 115-130 multi-request tests (~8% of 1,505, labelled estimate) covering the highest-risk behaviors the plan itself names as port hazards (retry, pagination MAX_PAGES, lookup-table orchestration, region probe). Deferring all of them to Layer 3 would remove wire-vector coverage exactly where R2.5/R6.1 need it. Extending the schema costs one array.
- One-WIRE-vector-per-test keeps `source_test` ↔ wire-vector 1:1, makes ids deterministic (D3), and matches how the Python runner re-executes (setup calls + one measured call per vector, D7). Builder vectors emitted from the same test coexist under `-N` ordinals (D1.3).
- Schema shape (see `vector.schema.json`): `expect.interactions` is an ordered array of `{request, response}` pairs, where `response` is either `{status, headers?, body}` or `{transport_error: "<httpx class name>"}`. The single-interaction case is the same array with length 1 (`expect.request`/`given_response` from the Appendix-A sketch are folded into `interactions[0]` — justified extension, documented in the schema `$comment`).
- Unordered batches (replays CDN walker, asyncio.gather — recon §7 hazard 4): an interaction group may set `"unordered_group": <int>`; interactions sharing a group id are compared as a multiset keyed by `(method, path, params)`, mirroring the tests' own `sorted(call_log)` convention (test_replays_service.py:196). The TS runner replays CDN-walker vectors with `concurrency = <recorded value>` carried in `call.input`; comparison never depends on intra-group order. Two corollaries the first draft missed: (a) **emit-side determinism** — `emit.py` sorts group members by their canonical `(method, path, params)` key before writing JSONL, otherwise `asyncio.gather` nondeterminism makes every re-extraction of a CDN vector a spurious D8 drift diff; (b) **replay-side serving is KEYED, not positional** — within an unordered group, `VectorTransport`/`VectorFetch` serve the recorded response whose `(method, path, params)` matches the incoming request (each recorded interaction consumable once), because the i-th replay request need not be the i-th recorded request (D7/D12).

Excluded multi-request sub-families (deferred to Layer 3 with logged exclusion counts in the manifest, category `layer3_deferred`):
1. **Wall-clock/backoff timing assertions** — vectors capture the request *sequence* of a 429-retry (attempt count, Retry-After honored via the sequence), never sleep durations (retry math itself is Layer-3 per plan §5 Layer 3).
2. **MAX_PAGES=50-patched guard test** (test_pagination.py:338-378) — depends on `unittest.mock.patch` of a module constant; a vector cannot express "patch MAX_PAGES first". Layer-3 translated test instead. Ordinary 2-3 page cursor pagination vectors ARE recorded.
3. **OAuthFlow.login PKCE end-to-end** — code_verifier/state random per run (recon §7 hazard 5); refresh-token requests (deterministic, exact body asserted at test_auth_flow.py:527-528) ARE recorded; interactive login is Layer 3 + Layer 4.

Streaming (JSONL export): one request, chunked body. The vector records `response.body_stream` as an array of base64/utf8 chunk strings preserving the mock's chunk boundaries (captured by the D1.1 stream tee; the gzip chunk-boundary handling in `_iter_jsonl_lines` is a named port target, plan §4.1), and `expect.result` records the parsed items the library yielded. `_IterableByteStream` tests driving a RAW `httpx.Client` (test_api_client.py:2680-2703, :2795-2843) DO pass through MockTransport but have no library entry point on-stack — they are excluded as `raw_transport_no_entrypoint` (D1.3), and the chunk-reassembly contract gets hand-authored `builder`-kind vectors against `_iter_jsonl_lines` via the registry instead (D4).

## D3 Corpus layout & regeneration story

**Decision: a new top-level `conformance/` directory in the Python repo (NOT under `context/`), per-source-file vector BUNDLES, deterministic ids, manifest with commit stamp.** Top-level because plan §5 Layer 1 says vectors live "in the Python repo at `conformance/` (D5)", and CI path filters must include it (recon `test-infra-ci.md` §4: `context/` would never trigger CI). This resolves the recon open question "where will the committed corpus live".

```
conformance/
├── record/                 # the pytest plugin (D1) + registry (D4) + codecs
├── runner/                 # Python corpus runner (D7)
├── smoke/                  # deliberate-break smoke test (D9)
├── vectors/
│   ├── manifest.json
│   ├── api-index.json                     # every call.api + signature shape (D4.4; consumed by TS-4)
│   ├── enums/bookmark_enums.json          # D4.2 item 10 snapshot
│   ├── <capability>/<source-file-stem>.jsonl   # e.g. funnels/test_build_funnel_params.jsonl
│   └── authored/<capability>/<name>.jsonl      # hand-written seed vectors (D4.3, D13)
└── schema/vector.schema.json               # copied from context/phase1/design at build time; single source of truth thereafter
```

- **Bundling**: one JSON Lines file per (capability, source test file) pair — per-test files would mean ~3,000+ tiny files (git noise, slow CI checkout); one monolith would make diffs unreviewable. JSONL: one vector per line, sorted by `id`, canonical JSON serialization (sorted keys, UTF-8, no trailing spaces) so re-extraction produces byte-identical files when behavior is unchanged.
- **Capability taxonomy** (top-level dirs): `segmentation`, `funnels`, `flows`, `retention`, `engage`, `cohorts`, `filters`, `bookmarks`, `entities` (App-API CRUD incl. dashboards/annotations/webhooks/flags/experiments/alerts/lexicon), `data-governance`, `replays`, `discovery`, `auth`, `pagination`, `streaming`, `validation`, `enums`, `compat` (pythonCompat/hello-world), `parse`. Assigned by the registry `capability` field for builders and by an endpoint→capability table in `emit.py` for wire vectors.
- **Vector id determinism**: `id = "<capability>/<module-or-api>/<slug>"` where `slug` is derived from the FULL pytest nodeid — module path stem + test class (if any) + function name + parametrization id — sanitized (`[^a-z0-9_-]` → `-`, lowercased). Function-name-only slugs collide: 838 tests across 60 files share a method name with another test in the same file (e.g. tests/test_user_builders.py:101/:117 both `test_integer_value` in different classes); full-nodeid slugs are collision-free by construction EXCEPT for case-only parametrize-id clashes (`[A]` vs `[a]`) introduced by lowercasing. Therefore `emit.py` runs a global id-collision pass over all collected nodeids before writing: any two DIFFERENT nodeids whose slugs collide each get a `-h<first-8-hex-of-sha1(nodeid)>` suffix (deterministic, both colliders suffixed). Duplicate ids in the final corpus are a hard emit-time error. Multiple vectors from the SAME nodeid (builder invoked twice, dual-seam builder+wire) get a `-N` ordinal suffix in call order (deterministic under serial execution; the suite has no xdist — pyproject.toml:140; ordinals count only OUTERMOST captures per the D1.2 re-entrancy guard, so they cannot churn on internal refactors).
- **manifest.json** fields: `schema_version`, `source_commit` (full 40-char SHA — 52696743b913a0c4c152deb48af987ae412b5aee for the first extraction; **injected externally via `--mp-record-commit` / `CONFORMANCE_RECORD_COMMIT`, exactly like the date — NEVER read from `git rev-parse` at record time**, so the D8 drift re-extraction at PR HEAD reproduces the committed stamps byte-for-byte by passing the committed manifest's own values back in), `extraction_date` (passed in externally via `--mp-record-date` / `CONFORMANCE_RECORD_DATE`, NOT read from the wall clock), `counts` (per kind, per capability, total, `with_setup`), `record_epoch` (the frozen clock from D1.4), `exclusions` (per D10 category with counts), `tool_versions` (python, httpx, pydantic, hypothesis — pydantic pinned because bookmark_schema messages are version-dependent).
- **Per-file stamp**: each `.jsonl` bundle's first line is a header object `{"$bundle": {"source_commit": ..., "source_file": ..., "count": N}}`.
- **Regeneration story (post-PR #206 merge)**: PR #206 is already merged INTO this branch's history (commit 5269674 sits on top of it); plan open-question 4 says "merge before running vector extraction". When `fix/latent-bugs-stress-test`/`ts-port/phase1-verification-rig` content reaches `main`, re-run extraction on the merge commit: `just conformance-record` → diff `conformance/vectors/` → commit if changed with the new `source_commit`. The TS repo pins `source_commit` in its runner config (D12) and bumps deliberately. A `conformance/record/README.md` documents the exact regeneration command line.

### D4.4 Registry format
`conformance/record/registry.py` exposes `REGISTRY: tuple[RegistryEntry, ...]` where `RegistryEntry` is a frozen dataclass:
```python
@dataclass(frozen=True)
class RegistryEntry:
    api: str              # dotted vector name, e.g. "workspace.build_funnel_params" or "segfilter.build_segfilter_entry"
    target: str           # import path "mixpanel_headless._internal.segfilter:build_segfilter_entry" or "mixpanel_headless.workspace:Workspace.build_funnel_params"
    kind: str             # "builder" | "validator"
    capability: str       # corpus directory, e.g. "funnels", "filters", "engage"
    input_codec: str      # "kwargs" (default) | named custom codec for Filter/dataclass args
    output_codec: str     # "json" (default) | "selector_str" | "validation_errors" | "datetime_dict" | ...
```
Input encoding: dataclass/Pydantic arguments (`Filter`, `FunnelStep`, `UserAction`, `CohortDefinition`, …) are serialized via a per-type codec table in `conformance/record/codecs.py` that emits `{"$type": "Filter", ...fields}` tagged objects; the TS runner has the mirror table (D12). This is a schema extension over Appendix A (`call.input` values may be `$type`-tagged) — justified because facade kwargs accept rich dataclasses (workspace.py:2412 signature) and plain JSON cannot round-trip them unambiguously.

Two non-dataclass codecs the wire registry additionally requires:
- **bytes**: `{"$type": "bytes", "encoding": "base64", "data": ...}` — `upload_to_signed_url(url, csv_bytes: bytes)` (api_client.py:7606) puts bytes in `call.input`; `download_lookup_table` returns bytes (api_client.py:7855-7861) so `expect.result` needs the same tagging (encoding rule added to D6). Request-side binary bodies use `expectedRequest.body_base64`; binary mock-response bodies use `givenResponse.body_base64` (schema).
- **callback**: `{"$type": "callback", "name": "<kwarg>"}` — function-valued kwargs (`export_events(on_batch=...)`, test_api_client.py:1408-1452; replay `label_fn`; progress callbacks) are unserializable as data but carry contract in their OBSERVED CALLS (the retry-state-reset contract — batch counts restarting across a 429 retry — lives entirely in `on_batch`'s call log). Replay semantics in BOTH runners: inject a recording stub for each callback-tagged kwarg; the stub's call log (positional args, canonicalized) is diffed against `expect.callback_calls[<kwarg>]` (new schema field). Callbacks whose recorded call log contains unserializable arguments abort emission of that vector into manifest category `unserializable_input` (backstop — none known today).

**api-index sidecar**: `emit.py` writes `conformance/vectors/api-index.json` — every distinct `call.api` in the corpus with its registry `kind`, target module, parameter names (positional order + kw-only, read from `inspect.signature` of the wrapped callable), and capability. This is the machine-readable authority the TS runner's api-map generation consumes for every NON-Workspace entry point (T1 in the review cycle: `context/typescript-port-api-map.json` covers only `workspace_members` + bare `exports`, so `api_client.*`/`replays.*`/`oauth_flow.*`/`region_probe.*` names — and their positional signatures, e.g. `update_annotation(annotation_id, body)` — were otherwise unresolvable). The index also defines the "module known" universe for the `UNPORTED` verdict (D12).

## D5 Session canonicalization & redaction

**Decision: vectors embed a normalized `call.session` object derived from the actual Session the recorded client carried; the credential allow-list is derived PER VECTOR from that same session (never from a fixed literal table); auth headers are matched by pattern; emitted request headers are ALLOWLISTED.**

Reference fake session (tests/conftest.py:65-129 `make_session()`: `test_user`/`test_secret`, `test[-oauth]-token`, `Project(id="12345")`, region `us`) is the COMMON case, but the suite uses dozens of other short fake credentials — census: `username="u"` ×101, `SecretStr("s")` ×91, `test_user` only ×56, plus `team.sa`/`sa-secret`/`u1`/`s1`/`brw-tok`/`my-oauth-token`/`eu-token` etc. (~51 more sites), including wire-relevant tests (test_workspace_lazy_resolve.py, test_account_three_types.py). A fixed known-credential table would abort extraction on the first of these; all credential rules below are therefore session-relative.

Rules:
1. The recorder serializes the session ACTUALLY bound to the client that made the request (`client._session` at record time), not a global assumption. This is mandatory because Workspace-facade tests intentionally use TWO different sessions — the injected client carries an oauth_token session while `Workspace(session=_TEST_SESSION)` carries a ServiceAccount with `default_project="12345"` (test_workspace_crud.py:50-100). The vector's `call.session` is what the TS runner must construct for its client; a separate optional `call.workspace_session` carries the facade session when they differ. Session fields (username/secret/token) are recorded VERBATIM — they are fake test values whatever their spelling; rule 4 is the real-secret tripwire.
2. **Auth headers in `expect.interactions[].request.headers_contain` are stored as patterns, not values** (plan Appendix A canonicalization: "auth headers matched by pattern not value"), and the pattern is GENERATED FROM THE BOUND SESSION: service_account → `^Basic <regex-escaped base64(username:secret)>$` computed from the rule-1 session (for the common conftest session that is `^Basic dGVzdF91c2VyOnRlc3Rfc2VjcmV0$`, locked by test_api_client.py:174-185); oauth → `^Bearer <regex-escaped token>$`. **Abort rule (session-relative)**: any observed `authorization` value that does NOT decode to the credentials of the session bound to the requesting client aborts the record run with an error — that is either a recorder attribution bug or credential leakage from the environment (tests/live/conftest_042.py:22-style; recon `parse-fixtures.md` risk). Fake-but-unusual credentials pass by construction because the comparison is against the bound session, not a table.
3. Header keys are stored lowercase (httpx lowercases in `dict(request.headers)`; recon §7 hazard 10); comparison is case-insensitive on the TS side by lowercasing before diff.
4. Redaction denylist scanned over EVERY emitted vector (belt-and-braces, and the REAL-secret tripwire now that rule 2 is session-relative): any string with base64/hex shape AND length ≥40 that is not derivable from the bound session's credentials, `sk-` prefixes, `Bearer ` followed by a token not equal to the bound session's token, absolute home paths (`/Users/`, `/home/`). Hits fail extraction loudly (never silently scrub).
5. `SecretStr` values in captured builder inputs/outputs serialize as their revealed literal (they are fake test values); rule-4 entropy/length screening applies to them like any other string.
6. **Request-header emission ALLOWLIST** (normative for `emit.py`): `headers_contain` records ONLY headers the library or the test explicitly set — `authorization` (as rule-2 pattern), `content-type` (when the library set it), custom headers the test injected (e.g. `MP_CUSTOM_HEADER_*`-derived), and `accept-encoding` ONLY when it differs from httpx's default (the export stream sets exactly `"gzip"`, api_client.py:1856 — recorded with `"node_only": true` sibling flag in the vector, because browser fetch cannot set it; the Phase-1 runner is Node so it is asserted there and skipped by a future browser runner). Transport-added headers (`host`, `accept`, default `accept-encoding`, `user-agent`, `content-length`, `connection`) are NEVER emitted: httpx adds them after the client seam, while the TS side's injected `VectorFetch` captures the `Request` BEFORE undici/browser internals add their equivalents — recording them would make every wire vector unfulfillable by any fetch implementation. `headers_contain` is subset-match by schema, so dropping them loses nothing the library controls. A canonical-selftest case (PR-4) proves unlisted headers are ignored on both sides.

## D6 Canonicalization algorithm (shared spec)

This is the normative algorithm BOTH runners implement (Python: `conformance/runner/canonical.py`; TS: `conformance-runner/src/canonical.ts`). Implementations must be behaviorally identical; the hello-world gate (D13) and a shared self-test file `conformance/schema/canonical-selftest.json` (input → canonical output pairs, ~40 cases) verify parity of the canonicalizers themselves.

Given a JSON-like value, `canonicalize(value, context)` produces a canonical UTF-8 JSON string:
1. **Objects**: keys sorted lexicographically by Unicode codepoint; **absent key ≠ key:null** — both are preserved as-is and compared distinctly (plan Appendix A; R3.5, R4.11). No key filtering except rules 6-8.
2. **Strings**: emitted verbatim, NFC/NFD untouched (rulebook §8.11); JSON escaping normalized to the minimal-escape form (`\uXXXX` only for control chars); no date re-parsing — dates stay the emitted strings (rulebook §8.5). **Lone surrogates are illegal in vectors** — the encoder rejects them at record time exactly like `NaN`/`Infinity` (rule 5): the canonical form is UTF-8, which cannot encode an unpaired surrogate, and the D14 bridge protocol would otherwise die mid-session on `json.dumps`-then-UTF-8-write.
3. **Numbers — canonical rendering is defined over the RAW JSON NUMBER TOKEN, not a parsed double.** Integers render without exponent or fraction (`18`, not `1.8e1`/`18.0`). A token with a fraction/exponent part renders via shortest-round-trip float rendering even when integral (`18.0` stays `"18.0"`): the canonicalizer does NOT unify `18.0` and `18` — whichever token the library serialized is the contract, EXCEPT in rule 4 positions. This is only implementable if both loaders see the raw token: the Python side already does (`json.loads` distinguishes int/float), and the TS loader is REQUIRED to use lossless number parsing (raw-text number capture, lossless-json-style — a TS-4 requirement, D12); plain `JSON.parse` would collapse `18.0` to `18` and round `> 2^53` integers silently, making both this rule and the `PRECISION_LOSS` verdict unimplementable.
4. **Numeric-string normalization — ONLY in segfilter number-filter operand positions (R10.11)**. Operand positions are identified STRUCTURALLY, not heuristically, by exactly one clause: any value at path `filter.operand` (or element of `filter.operand` when it is an array) inside an object that also has `selected_property_type: "number"` (segfilter.py `_build_number_filter`, :158). Normalization: parse the string with the Python float grammar (reject if unparseable → no normalization), then render via shortest-round-trip and int-collapse (`"18.0"` → `"18"`, `"18.50"` → `"18.5"`). Applied to BOTH sides before diff. This is narrow and field-scoped per R10.11, whose server-coercion evidence covers segfilter operands ONLY. Explicitly NOT normalized: (a) bookmark `filterValue` in ANY dialect — legacy `filterValue` is raw passthrough in Python (`"filterValue": f._value`, bookmark_builders.py:~501) and R10.12's evidence says a string there is quoted into the selector as a string literal, i.e. `"18.0"` vs `18` are NOT server-equivalent in that position, so normalizing would let a TS builder that coerces user strings through `Number()` pass vectors while emitting a different selector (an earlier draft's rule 4b did this; deleted); (b) engage selector strings (one opaque string; escaping is contract char-for-char, rulebook §8.2).
5. **Floats** elsewhere: shortest-round-trip decimal rendering (Python `repr`, JS default `String(n)` — these agree for all finite doubles except the exponent-threshold window; the canonicalizer implements ONE rule: ECMAScript `Number::toString` semantics, and the Python side uses `repr(float)` then converts Python's exponent forms to the JS form — the conversion table lives in the selftest file). **Negative zero**: rendered `"-0.0"` (sign-preserving; matches Python `repr(-0.0)`; the TS canonicalizer must special-case it because ECMAScript `String(-0)` is `"0"` — implementable because rule 3 gives it the raw token). `-0.0` is a mandatory canonical-selftest case. `NaN`/`Infinity` are illegal in vectors (encoder rejects at record time).
6. **Error objects (R5.4)**: before diffing any `expect.error`, drop `message`, `suggestion`, `fix` keys at KNOWN ERROR-OBJECT LEVELS ONLY — the top-level error object and each element of `errors[]` — NEVER recursively inside `details_contain` values (a server response body embedded at `details.response_body` may legitimately contain a `message` member that IS wire data, exceptions.py:154; recursive deletion on both sides would mask a port that drops or fabricates it, contradicting rule 1's absent≠null stance). Compare `class` (exception class name, R5.2), `code`, `path`, `severity` strictly.
7. **Auth headers**: values under `headers_contain.authorization` compared by the vector's stored regex pattern (D5.2), not string equality.
8. **Header keys** lowercased on both sides before comparison (D5.3).
9. **Unordered groups** (D2): interactions sharing `unordered_group` are canonicalized individually, then the group is sorted by canonical string before sequence comparison. The SAME sort is applied by `emit.py` at write time (emit-side determinism, D2) so re-extraction is byte-stable.
10. **$type-tagged inputs** (D4.4) are decode-side concerns; canonicalization treats them as ordinary objects (they appear only in `call.input`, which is replayed, not diffed).
11. **bytes values** in `expect.result`/`expect.output` are encoded as `{"$type": "bytes", "encoding": "base64", "data": ...}` (D4.4) and compared as ordinary objects.

Comparison = string equality of the two canonical forms. `PRECISION_LOSS`: the TS loader's lossless number parsing (rule 3) flags any integer token whose value is not exactly representable as a JS double (`> 2^53` magnitude); when the TS LIBRARY's own output must round such a value, the vector FAILS with the distinct `PRECISION_LOSS` verdict (R4.5 escalation trigger). With `JSON.parse` this check would be vacuous — both sides would round identically and compare equal — which is why lossless parsing is a hard TS-4 requirement, not an optimization.

## D7 Python corpus-runner architecture

**Decision: a standalone runner package `conformance/runner/` that RE-EXECUTES library code from `call.input` for every vector — it never replays recordings against themselves. It must fail when `src/` is semantically mutated; that is its whole purpose (D9 proves it does).**

Execution model per `kind`:
- `builder` / `validation-error` (validator half): decode `call.input` via the codec table, import the target from `call.api` through the SAME registry the recorder used (`conformance/record/registry.py` — one registry, two consumers, so recorder and runner can never disagree about entry points), call it, canonicalize output (or the structured error), diff against `expect`.
- `wire`: construct a real `MixpanelAPIClient` (or `ReplaysService`/`OAuthFlow`/`probe_region` per `call.api` prefix) with a `VectorTransport(httpx.BaseTransport)` built from `expect.interactions[]`: for ORDERED interactions it serves interaction *i*'s recorded `response` (or raises the recorded `transport_error`) to request *i*; within an `unordered_group` it serves BY KEY — the recorded interaction whose `(method, path, params)` matches the incoming request, each consumable once (positional serving would hand CDN file bodies to the wrong URLs under async scheduling, D2) — while capturing every actual outgoing request for diffing. The runner then executes `call.setup[]` entries in order (state-mutating and prerequisite calls, D2) followed by the measured call in `call.api`+`call.input`; it diffs (a) each captured request against the recorded interaction sequence (multiset semantics inside unordered groups) and (b) the measured call's returned/raised value against `expect.result`/`expect.error`, plus (c) recorded-callback call logs against `expect.callback_calls` (D4.4). Served responses are canned; requests and results are live library behavior — mutations in URL building, param serialization, retry counting, pagination, parsing all surface as diffs. Extra or missing interactions anywhere across setup+measured fail the vector.
- `parse`: same as wire but only `expect.result` is diffed (request side is a fixed synthetic GET).
- Clock/UUID/sleep: the runner installs the same `RECORD_EPOCH` freeze, deterministic-UUID patch, AND virtual-sleep shim as record mode (D1.4) so re-execution is bit-stable and retry/backoff vectors replay instantly (no real exponential sleeps inside the ≤5-min budget).

Harness: a SINGLE pytest file `conformance/runner/test_corpus.py` with `pytest_generate_tests` parametrizing over every vector in `conformance/vectors/**` (id = vector id). Runs under the normal repo toolchain (`uv run pytest conformance/runner -o addopts=""`); ALSO exposed as a pytest-free CLI `python -m conformance.runner --vectors conformance/vectors [--filter <glob>] [--report json]` for the D9 worktree smoke test (pytest-free because bare `uv run` installs no pytest — recon `test-infra-ci.md` §3). NOTE the CLI is NOT dependency-free: it imports `mixpanel_headless` + `httpx` (base deps) AND `freezegun` for the D1.4 clock shim, which lives in the dev extras — so every environment that runs it (CI job, smoke worktrees) MUST `uv sync --all-extras` first (D9.2 step 2); the CLI fails fast with a clear `runner_crashed` report if `freezegun` is missing rather than silently skipping the freeze.

Runtime budget: each vector is one in-process library call against an in-memory transport; the analogous mocked suite runs ~6,769 tests in minutes. Budget: **≤5 minutes for ~3,000-4,000 vectors on CI hardware** (target; measured in task PR-8). If exceeded, first lever is collection cost (JSONL bundles load with one `json.loads` per line, no per-vector file I/O), not vector count.

## D8 CI wiring

**Decision: one new sibling job `conformance` in `.github/workflows/ci.yml`, Python 3.12 only, running (a) the corpus runner and (b) the record-mode drift check. Independent of the `test` job (parallel — it re-syncs its own env; recon `test-infra-ci.md` §4 endorses either, parallel is faster and a runner failure is meaningful even if `test` also fails).**

Job spec (mirrors existing steps at ci.yml L36-47):
```yaml
conformance:
  runs-on: ubuntu-latest
  steps:
    - checkout (actions/checkout v6.0.2)
    - setup-python 3.12 (v6.2.0)
    - setup-uv (v8.1.0); uv sync --all-extras
    - name: Typecheck conformance tooling      # D17.1
      run: uv run mypy conformance/
    - name: Conformance tooling unit tests     # D17.5
      run: uv run pytest conformance/tests -o addopts="" -q
    - name: Corpus runner
      run: uv run pytest conformance/runner -o addopts="" -q
    - name: Record-mode drift check
      run: |
        uv run pytest tests -p conformance.record.plugin \
          --mp-record-vectors=/tmp/re-extract \
          --mp-record-date=$(jq -r .extraction_date conformance/vectors/manifest.json) \
          --mp-record-commit=$(jq -r .source_commit conformance/vectors/manifest.json) \
          -o addopts="" -m "not live" $(cat conformance/record/exclusions.args)
        uv run python -m conformance.record.diff /tmp/re-extract conformance/vectors
      env: { HYPOTHESIS_PROFILE: ci }
```
- The drift check re-extracts and byte-diffs against the committed corpus (deterministic per D3: frozen clock, injected extraction date AND injected source-commit stamp — both read back from the committed manifest, so re-extraction at PR HEAD reproduces the stamps; reading `git rev-parse` at record time would make every PR fail by construction). Any diff fails the PR — this is plan §Phase-5's "standing CI contract" started early (Risk table: "Corpus and Python drift apart post-port").
- **`conformance.record.diff` semantics (normative)**: scope = the EXTRACTED subset only — `conformance/vectors/authored/**` and `conformance/vectors/enums/**` are excluded by path (record mode never emits them; a whole-tree diff would report them missing on every run; `enums/` is regenerated only by an explicit flag). Within scope the check is BIDIRECTIONAL: (1) bundle-path set equality (a bundle present on only one side fails), (2) per-vector-id set equality within each bundle (added/removed ids fail), (3) byte equality per vector line and per `$bundle` header, (4) manifest equality after dropping nothing (stamps are injected, so full byte equality applies). Any asymmetry in either direction fails.
- **Path filters**: add `conformance/**` to BOTH `paths:` lists (ci.yml:7-21); without this, corpus-only PRs never run CI (recon §4).
- Runtime: corpus runner ≤5 min (D7) + re-extraction ≈ one full non-live suite run (the `test` job already runs the suite 4×, so this stays within existing wall-clock norms). If re-extraction proves too slow for every PR, fallback (documented, not default): run the drift check only when `src/**` or `tests/**` changed.
- **`just check`**: append a `conformance` recipe (conformance/tests + corpus runner, NOT the drift re-extraction — keeps local `just check` fast) to the `check` dependency list (justfile L12); the justfile `typecheck` recipe gains `conformance/` in its arguments (D17.1), so every step of the CI conformance job except the drift check has a `just check` counterpart — one recipe/job matrix, no CI-only checks besides the drift re-extraction. `just conformance-record` and `just conformance-smoke` (D9) are separate manual recipes. This preserves "just check is a strict superset of CI" for the blocking parts; the drift check is CI-only but is itself derived purely from committed state, so a green `just check` + unchanged vectors implies green CI.

### D9.2 Mechanics
Script `conformance/smoke/run_smoke.py` + patch files `conformance/smoke/patches/S01..S13.patch` (unified diffs). For each patch:

3. `git -C /tmp/mp-smoke-SNN apply patches/SNN.patch`.
4. 5. `git worktree remove --force`.

### D9.3 Pass criterion and miss handling
- The runner CLI report distinguishes `vector_failed` (a vector executed and diffed red) from `runner_crashed` (nonzero exit, import error, unhandled exception before/outside vector execution). **A crash is NEVER a catch**: any `runner_crashed` in any run — control or sabotaged — is a smoke ERROR that fails the whole smoke test for infrastructure reasons, distinct from both PASS and MISS.
- PASS: the control run completes with 0 `vector_failed` and 0 crashes, AND every one of S1–S13 completes (no crash) with ≥1 `vector_failed`. The script prints a per-patch table `{patch, status: caught|missed|error, failing_vector_count, first_failing_id}`.
- MISS: a patch with 0 failing vectors is a corpus coverage hole. Response protocol: (1) locate the suite tests covering that line (they exist for all 13 — sites were chosen on tested paths); (2) if record mode excluded them (D10), author seed vectors under `conformance/vectors/authored/` exercising the area; (3) re-run only that patch. The smoke test is not "green by construction" — authored vectors must go through the Python runner like all others.
- **Where it lives / when it runs**: `conformance/smoke/`, runnable locally via `just conformance-smoke`. NOT a per-PR CI job (14 worktree+sync cycles — control + 13 patches ≈ tens of minutes). It is a documented RELEASE-GATE/manual check: required before (a) declaring the Phase-1 gate met (plan §6 Phase-1 gate), (b) every corpus regeneration commit (D3), and (c) the exit-criteria checklist (plan §6 "Judge validated"). The smoke script writes `conformance/smoke/last-run.json` (commit, date, per-patch results) which IS committed, giving CI-visible provenance without CI runtime cost.

## D12 TS conformance-runner design

**Workspace `conformance-runner/` (private, not published).**

- **Vector loading — SNAPSHOT, not a live cross-repo path**: the corpus is copied INTO the TS repo at `conformance-runner/corpus/` (committed) by `scripts/sync-corpus.sh`, which copies `conformance/vectors/**` (+ `canonical-selftest.json`, `api-index.json`) from the Python repo and verifies the copied `manifest.source_commit` matches `corpus.config.json`'s pinned `sourceCommit` before writing. Config: `{"vectorsPath": "./corpus", "sourceCommit": "<pinned SHA>", "recordEpoch": "2026-01-15T12:00:00Z"}`. Rationale: a relative path into the Python repo's WORKING TREE couples every TS conformance run (CI, D13 gate) to whatever branch that mutable dev checkout happens to have checked out — the corpus lives on a local never-pushed branch (D16), so a branch switch would break or silently skew the runner. The loader still verifies `manifest.source_commit === sourceCommit` and refuses on mismatch (drift protection); corpus refresh = re-run sync script + commit, keyed by the new SHA. This supersedes plan §4.1's "git submodule or published tarball" wording (snapshot-copy is the tarball option minus packaging; Discrepancy Log #12); published-artifact consumption (plan open question 2) remains a Phase-5 concern — `loadCorpus(path)` is artifact-shape-agnostic.
- **Vector parsing — LOSSLESS NUMBERS (hard TS-4 requirement, D6 rule 3)**: the JSONL loader must capture raw number tokens (lossless-json-style parsing), never bare `JSON.parse` — otherwise `18.0` vs `18` distinctions and the `PRECISION_LOSS` verdict (D6) are unimplementable and the two runners silently enforce different contracts.
- **Fetch interception: the injected-fetch seam (R2.4), NOT undici MockAgent globals.** Justification: (1) R2.4 makes `fetch?: typeof fetch` a first-class constructor input — the exact analog of `_transport=`, so vectors replay through the same seam production users inject, keeping the runner isomorphic (MockAgent is undici/Node-only and would silently exempt the browser build from conformance); (2) global interception can leak across concurrently-running vitest workers; (3) the Python recorder hooks the transport seam for the same reason (D1.1) — symmetric seams keep "when auth is resolved" observable per request (R2.8). A `VectorFetch` factory takes `expect.interactions[]` and returns a fetch impl that asserts sequence position (keyed `(method, path, params)` matching within `unordered_group`s, D2/D7), captures the outgoing `Request` (method/url/headers/body), and returns the canned `Response`. **`transport_error` replay shape**: `VectorFetch` rejects the way NATIVE fetch rejects — a `TypeError` with `cause`, selected from a committed httpx-class → fetch-rejection table (`conformance-runner/src/transport-errors.ts`) — NEVER a pre-mapped `MixpanelHttpError`: R2.10 puts the adapter's fetch-rejection → error-taxonomy mapping UNDER TEST (and e.g. the `upload_to_signed_url` port must itself wrap transport failures into `UPLOAD_ERROR`, api_client.py:7646-7651 / test_api_client_data_governance.py:2325 — throwing the mapped error would bypass exactly that code and risk double-wrapping). Streaming bodies rebuild `body_stream` chunks into a `ReadableStream` preserving chunk boundaries (D2). The runner installs the injectable `sleep` shim as a no-op/virtual sleep (mirror of D1.4/D7) so backoff vectors replay instantly. MSW/undici MockAgent may still be used in ordinary Layer-3 tests; the conformance runner itself uses only injected fetch.
- **Execution per kind** mirrors D7: `builder`/`validation-error` → decode `$type`-tagged inputs via the mirror codec table (`conformance-runner/src/codecs.ts`, incl. `bytes` and `callback` codecs per D4.4), call the mapped TS entry point, canonicalize, diff. `wire`/`parse` → construct the TS client with `VectorFetch` + the session from `call.session`, execute `call.setup[]` entries in order, invoke the mapped measured method, diff captured requests + result/error + `callback_calls`.

## D14 Differential bridges (JSON-RPC oracles)

**Protocol** (shared spec, `conformance/schema/oracle-protocol.md` is normative):
- Transport: newline-delimited JSON-RPC 2.0 over stdin/stdout (one request object per line, one response per line — LSP-style Content-Length framing rejected as needless for line-safe JSON; payloads never contain raw newlines because they are single-line JSON). `stderr` is free-form logs, never parsed. **Framing encoding: ASCII-safe** — oracle-py serializes with `ensure_ascii=True` (and oracle-ts escapes all non-ASCII), so a lone-surrogate string generated by a fuzz strategy can never kill the bridge mid-session via a UTF-8 `UnicodeEncodeError` on stdout; lone surrogates are additionally REJECTED by the D6 rule-2 encoder on both sides (a strategy that generates one gets a protocol-level `error`, not a hang or crash).
- Methods: `oracle.info` (→ `{language, library_version, source_commit, protocol_version}`), `oracle.call` (`params: {api: <python dotted name>, input: {...$type-tagged...}, session?: {...}}` → `{ok: true, output: <canonical JSON>}` or `{ok: false, error: {class, code, errors?: [{path, code, severity}]}}`), `oracle.shutdown`. Method naming stays language-neutral: `api` uses the PYTHON dotted name on both sides; oracle-ts applies the same naming map as the runner (D12).
- Error mapping per R5.4: expected library errors are DATA (the `ok:false` payload with class name + code, messages stripped); only harness bugs surface as JSON-RPC `error` objects (code -32000 range). This keeps "Python raised V7 / TS raised V7" a comparable value, not an RPC failure.

**oracle-py**: lives at `conformance/oracle_py/` in the Python repo (decided: under `conformance/`, NOT a top-level `differential/` — it shares the registry, codecs, and canonicalizer with the runner and must ride the same mypy/ruff scope, D17; a second top-level dir buys nothing). Entry point `python -m conformance.oracle_py`. v1 surface = exactly the D4 BUILDER-side registry entries (5 facades + module-level builders/validators/serializers + pythonCompat reference fns incl. the D13 wirestub); `wire_api`/`wire_state` registry entries are OUT of oracle scope in Phase 1 (fuzzing wire calls needs a transport story — Phase 3 concern); `oracle.call` resolves `api` through the registry, same codecs, same frozen clock/UUID env as D7.

**oracle-ts**: lives at `differential/oracle/` in the TS repo. Phase-1 scope: protocol conformance (info/call/shutdown, error mapping) + the D13 compat module ONLY; every other `api` returns `{ok: false, error: {class: "Unported", code: "UNPORTED"}}` which the harness counts as skip, not divergence. Grows with each Phase-3 batch.

**Hypothesis harness**: `conformance/differential/fuzz_harness.py` (Python repo — Hypothesis lives here). It spawns both bridges as subprocesses, generates inputs, calls both, canonicalizes (D6 impl), diffs; divergence → shrunken repro written to `conformance/differential/repros/<date>-<api>.json`. Strategy source: the suite's 41 `@st.composite` strategies live INSIDE test files (13 files; recon test-infra-ci §2 — no shared strategies module). Reuse mechanism: import them directly from the test modules (`from tests.test_user_query_pbt import filters as filter_strategy` etc.) — tests are importable as modules since `testpaths` packages carry `__init__.py`; where an import proves entangled with fixtures, the harness VENDORS a copy into `conformance/differential/strategies.py` with a header comment naming the source test file + line (kept in sync manually; acceptable because strategies change rarely). Phase-1 priority targets (plan Layer 2): `filter_to_selector`/`filters_to_selector` (escaping), `build_segfilter_entry`, `build_filter_entry`, validators by code, `normalize_on_expression`, pythonCompat. Every generated corpus must include the R10.9 mandatory edge set (integral float, fractional float, True, None, empty list, empty string, non-BMP string, every error branch) as explicit `@example` decorators.
Phase-1 done-criterion for the harness: runs green against oracle-py↔oracle-py (self-parity, proves plumbing) and oracle-py↔oracle-ts for the compat module.
