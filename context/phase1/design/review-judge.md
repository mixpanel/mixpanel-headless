# Adversarial Review — Judge Validity Lens (D6–D9, D17)

Reviewer question: could the corpus pass while the code is wrong? Attack surfaces: tautological replay, canonicalization over-normalization, deliberate-break smoke-test shallowness, CI drift-check loopholes, D17 gate interactions.

Design under review: `context/phase1/design/phase1-design.md`, `vector.schema.json`, `naming-map.md` at branch `fix/latent-bugs-stress-test` @ 5269674. All repo citations verified at that commit.

---

## F1 (BLOCKER) — Wire vectors have no specified capture seam for `call.api` / `call.input` / `expect.result`; the natural workaround is exactly the tautology/lossy-reconstruction the design forbids

- D1.1 records only the transport (`httpx.MockTransport.handle_request` wrap). D1.2's registry wrap is explicitly scoped to "pure builders (kind `builder` / `validation-error`)" (phase1-design.md:42), and D4.1/D4.2 list only builders/validators — no `api_client.get_events`, no `LiveQueryService.query_funnel`, no `Workspace` CRUD methods.
- Yet the wire runner (D7, phase1-design.md:204) requires `call.api` + `call.input` to "invoke the library call for real" and `expect.result` to diff the return value, and D2 (line 78) requires `expect.result` = "the parsed items the library yielded". The schema makes `call.api`/`call.input` REQUIRED (vector.schema.json:28). Nowhere in D1–D5 is a mechanism specified that observes which public method the test called, with which kwargs, or what it returned. Grep of the design for a wire entry-point wrap comes up empty; D1.3 classification is "by observed seam firing" only.
- Failure scenarios:
  1. PR-2 implementers, having only transport recordings, reverse-engineer `call.input` from the captured request (params → kwargs). That is lossy for defaulted parameters: `get_events` computes `to_date=today` internally (api_client.py:2380); a reconstructed input carries the date as an EXPLICIT kwarg, so a mutant that breaks the default-date computation replays green — the corpus passes while the code is wrong.
  2. Or `expect.result` is synthesized from the recorded response body (recording compared to recording) — the literal tautological replay this review was told to hunt; D7's "never replays recordings against themselves" is an assertion, not a mechanism.
- Blast radius: 6 of the 12 D9 smoke patches (S3, S4, S6, S10, S11, S12) are detectable ONLY via wire vectors; with F1 unresolved, half the judge-validation matrix has no defined data source. The ~1,400 wire-classified tests (D10 sanity target) are the majority of the corpus.
- Fix direction: a third seam must be designed — e.g. a wire-API registry (client/service/facade public methods) wrapped like D4.4 entries, with input codecs for their kwargs, plus a rule for which frame wins when a Workspace facade delegates to api_client (outermost wrapped call).

## F2 (BLOCKER) — The D8 drift check can never pass as specified: `source_commit` stamps and authored vectors make re-extraction byte-differ on every PR

- D3 stamps `source_commit` (the extraction commit SHA) into `manifest.json` AND into the first line of EVERY bundle (`{"$bundle": {"source_commit": ...}}`, phase1-design.md:101). D3's determinism claim is explicitly "re-extraction at the same commit is byte-identical" (line 100) — only the extraction DATE is injected externally; the commit is not.
- D8 runs the drift check on every PR: re-extract to `/tmp/re-extract`, then "byte-diffs against the committed corpus. Any diff fails the PR" (lines 227–234). A PR's HEAD SHA always differs from the committed corpus's extraction SHA, so the re-extracted manifest and every single bundle header differ byte-wise → the gate is red on every PR from the moment it is wired (including PR-9 itself, whose HEAD postdates the PR-5 extraction commit). An always-failing gate is a useless verdict; the predictable field fix (ignore "whatever differs") silently weakens the check.
- Second leg: `conformance/vectors/authored/**` (D13 compat vectors, 9 uncovered validation codes, phase008 parse, `_iter_jsonl_lines` chunks) and `enums/bookmark_enums.json` are hand-written/one-time artifacts that record-mode re-extraction does NOT emit. A whole-tree byte-diff therefore reports them as missing on every run once PR-7 lands. The design never says the diff excludes `authored/` and `enums/`.
- Fix direction: inject `--mp-record-commit` like the date (or strip commit stamps before diffing), and specify the diff as: extracted-tree ↔ extracted-subset-of-committed-tree, bidirectional (added AND removed files/vectors both fail — see F9).

## F3 (MAJOR) — D9 smoke mechanics: the worktree runner env lacks freezegun (and possibly the clock shim entirely); a crashed runner is indistinguishable from "sabotage caught"; control-run venue unspecified

- D7 claims the pytest-free CLI "imports only `mixpanel_headless` + `httpx`, both base deps" (phase1-design.md:208), but D7 also requires the runner to install "the same `RECORD_EPOCH` freeze and deterministic-UUID patch as record mode (D1.4)" (line 206) — and D1.4's freeze is freezegun (line 51), which D17.7 adds to `[project.optional-dependencies].dev` (pyproject.toml:42-54). Verified: bare `uv run` in a worktree installs base deps + `[dependency-groups].dev` only (pyproject.toml:182-189 — click-man/pre-commit/psutil/ruff/types-psutil; recon test-infra-ci.md:70-72 "43 pkgs, no pytest"). Extras are NOT synced. So the D9.2 step-3 command (`cd /tmp/mp-smoke-SNN && uv run python -m conformance.runner ...`) hits `ModuleNotFoundError: freezegun` — on all 12 sabotage runs. (Clock freeze is not optional: date-defaulting vectors, e.g. funnel 30-day windows at api_client.py:2937-2948, fail without it.)
- Judge-validity kill shot: D9.3's PASS criterion is "every one of S1–S12 yields ≥1 failing vector AND the unpatched control run yields 0 failures" (line 269). The mechanics (D9.2) describe worktrees only for the PATCHED runs; the control run's venue is unspecified. If the control runs in the main checkout (dev extras present → green) while every patched worktree run crashes on import (nonzero exit → counted as "failing vectors"), the smoke test PASSES 12/12 while never executing a single sabotaged code path. The check would certify a judge that was never tested.
- Fix direction: control run must use the identical worktree procedure minus the patch; the report must distinguish `vector_failed` from `runner_crashed` and treat crashes as smoke-test ERRORS, not catches; the worktree bootstrap must be `uv sync --all-extras` (or move freezegun to `[dependency-groups]`).

## F4 (MAJOR) — Worktree pinned to `<commit-of-corpus-manifest>` predates the runner and authored vectors: the smoke test executes the wrong tree state

- D9.2 step 1: `git worktree add /tmp/mp-smoke-SNN <commit-of-corpus-manifest>` (phase1-design.md:263). Per D16's commit sequence, the corpus manifest lands in commit 4 ("first extraction") while the corpus runner is commit 5 and authored vectors commit 6 (lines 400-402). A worktree at commit 4 has NO `conformance/runner` package — `python -m conformance.runner` (resolved from worktree cwd) fails immediately for every patch. Combined with F3's crash-counting ambiguity, this can again produce a vacuous 12/12 "pass".
- Even with orderings fixed, pinning the worktree to the corpus commit rather than the branch HEAD means post-regeneration `src/` commits are never what gets sabotaged — the smoke test certifies stale library code. The correct spec: worktree at the SAME ref as the control run (HEAD), with the corpus read from that ref's committed `conformance/vectors` (which is already pinned to its own extraction commit by the manifest).

## F5 (MAJOR) — D6 rule 4b scope-creeps R10.11 into bookmark `filterValue`, against the rulebook's own evidence: a real TS defect would pass vectors

- R10.11 (rulebook:282-291) resolves `"18"`≡`"18.0"` for **number-type segfilter operands** only, with server-coercion evidence specific to `segfilter_to_property_filter.py`, and states the policy: "the conformance canonicalizer normalizes numeric strings ONLY in number-filter operand positions (narrow, field-scoped — not a general weakening)." The operand site is `str(value)` at segfilter.py:183 — rule 4a is correctly scoped to it.
- D6 rule 4b (phase1-design.md:186) additionally normalizes bookmark `filterValue` string elements when `propertyType: "number"`. But Python never stringifies `filterValue` — it is a raw passthrough (`"filterValue": f._value`, bookmark_builders.py:501), so any string there is user-supplied data. And R10.12's evidence points the other way: `filterValue` is "passed through as-is (`backend/util/arb_selector.py:1862`) and a string would be quoted into the selector as a string literal" — meaning `"18.0"` and `"18"` produce DIFFERENT selectors. No server-coercion evidence for legacy filterValue is cited anywhere.
- Concrete slipping mutant: a TS builder that round-trips user filter values through `Number()` (emitting `"18.5"` where the user — and Python — passed `"18.50"`, or `"18"` for `"18.0"`) passes every vector because rule 4b normalizes both sides, yet emits a semantically different bookmark server-side. Wrong-pass, exactly the over-normalization failure mode this rule family was supposed to avoid.
- Fix: delete rule 4b (or gate it on positive evidence about legacy-dialect coercion); keep normalization strictly at the segfilter `filter.operand` position per R10.11.

## F6 (MAJOR) — D6 rule 3 ("does NOT unify 18.0 and 18") and the PRECISION_LOSS verdict are unimplementable in the TS runner as designed; integral-float and >2^53 fidelity silently vanish

- Rule 3 (phase1-design.md:183): "the canonicalizer does NOT unify `18.0` and `18`; whichever string the library serialized is the contract." But canonicalizers operate on PARSED values. The vector file preserves `18.0` as text; the D12 loader is specified as plain "JSONL parse" (line 447) — `JSON.parse` collapses `18.0` → Number 18 with no trace. The TS side canonicalizes both expectation and actual to `"18"` under rule 5's ECMAScript rendering, so the distinction rule 3 declares contractual is unobservable in the TS runner. Meanwhile the Python runner sees `float 18.0` → `"18.0"`. The two runners implement DIFFERENT effective contracts for the same vector — the cross-language gate is weaker than the spec claims, on the port hazard (§8 item 3 / R11.2) the design itself calls highest-frequency.
- Same root cause kills `PRECISION_LOSS` (line 196): "precision loss detected while parsing a number > 2^53" — `JSON.parse` cannot detect it; `9007199254740993` silently becomes `...992` in both the loaded expectation and the TS library output, they compare equal, and the R4.5 escalation trigger never fires. Concrete slipping vector: any mock body carrying a large numeric id.
- Fix direction: D12's loader must parse JSON losslessly (raw-text number capture, e.g. `lossless-json`-style reviver over source offsets) — this is a real, rework-expensive requirement that must be designed in, not discovered at TS-4.

## F7 (MAJOR) — D10's `layer3_deferred` sleep-patch heuristic excludes the ONLY tests covering the per-paginator 429 retry (an R6.1 named invariant); a paginator-retry-removal mutant passes the corpus and no smoke patch covers it

- D10 defers "timing-assertion tests detected by `unittest.mock.patch("time.sleep")`" (phase1-design.md:285). Verified: EVERY pagination-429 test routes through `patch("time.sleep")` — test_pagination.py:444 (`test_http_429_mid_pagination`) and the shared helper at :693 used by the entire Retry-After defensive class (:705-815). Under the heuristic, all of them are excluded → zero wire vectors on `pagination.py`'s per-paginator retry path, which R6.1 explicitly names as preserved behavior ("per-paginator 429 retry (3 attempts) preserved").
- Concrete slipping mutant: TS port (or Python sabotage) deletes the paginator's 429 retry → every remaining pagination vector (plain 2-3 page cursor walks) still passes; S6 tests the cursor guard, S12 tests `_execute_with_retry` in api_client (`range(self._max_retries + 1)`, api_client.py:747) — neither touches the paginator's own retry loop. Nothing in D9's matrix detects the hole.
- The heuristic is simultaneously under-inclusive: api_client's actual timing-assertion tests use a `monkeypatch`-based sleep-capture fixture (test_api_client.py:3472-3481), not `unittest.mock.patch("time.sleep")`, so the rule as stated wouldn't detect the very family it was written for. (Recording those is harmless — sequence, not time — which further shows "patches sleep" is the wrong discriminator; "asserts on sleep durations" is.)
- Secondary: neither D7 nor D8 no-ops `time.sleep` during REPLAY. Retry vectors recorded from tests with no `Retry-After` header (test_api_client.py:460-470) will really sleep the exponential backoff in the corpus runner (and the TS runner needs an injectable sleep the design never mentions) — a per-vector multi-second stall inside a ≤5-min budget.

## F8 (MAJOR) — Multi-library-call wire tests are unrepresentable in the one-call-per-vector model, and session-only capture misses client-attribute state (`set_workspace_id`)

- D2 fixes "one vector per TEST" with a single `call.api`/`call.input`, and D7 replays "one library call per vector". Measured: 38 tests in `tests/unit/test_api_client*.py`+`test_workspace*.py` alone invoke ≥2 distinct client/ws methods (script over test bodies; e.g. `test_posts_to_stream_bookmark_endpoint` calls `set_workspace_id` then `activity_feed`). The design never says what the recorder does with the second call: overwrite, `-N` suffix a second WIRE vector (then interaction attribution across the two calls is undefined), or drop.
- The dominant pattern — `client.set_workspace_id(789)` then a query — is state the vector cannot carry: `set_workspace_id` stores on `self._workspace_id`, a client attribute (api_client.py:1418), NOT on `client._session`, which is all D5.1 captures. The replayed client therefore builds `/projects/{id}/...` paths where the recording shows `/workspaces/789/...` → these vectors fail the CONTROL run. Loud, not silent — but the triage-time response ("exclude tests the recorder can't model") quietly deletes wire coverage of workspace-scoped paths, and neither D2's exclusion list nor D10's categories has a bucket for it, so the manifest wouldn't even count the loss.
- Fix direction: either vector-per-library-call with interaction slicing by call boundary, or a `call.setup[]` field for state-mutating pre-calls; and capture effective client state (workspace id) alongside the session.

## F9 (MINOR) — D6 rule 6 strips `message`/`suggestion`/`fix` "anywhere in the error subtree", which reaches into `details_contain` wire data and masks presence/absence diffs

- R5.4 licenses stripping MESSAGE TEXT; D6 rule 6 (phase1-design.md:190) deletes any key literally named `message`/`suggestion`/`fix` recursively. `expect.error.details_contain` may embed server payloads: `details["response_body"]` is a real detail field (exceptions.py:154), and Mixpanel error bodies can carry a `message` member. Stripping it from BOTH sides means a TS port that drops or mangles `response_body.message` (or emits a spurious one) compares equal — and because stripping runs before diff, even present-vs-absent for those keys becomes unobservable, contradicting D6 rule 1's absent≠null stance for everything else.
- Fix: strip only at known error-object levels (top-level error, `errors[]` elements), never inside `details_contain` values.

## F10 (MINOR) — Drift-diff semantics for added/removed vectors unspecified

- `conformance.record.diff /tmp/re-extract conformance/vectors` (phase1-design.md:231) has no stated directionality. A per-file compare iterating one side misses files that exist only on the other (new test file → new bundle; deleted test → vanished bundle), and within a bundle, a naive line-zip can misreport pure insertions as wholesale diffs (noise) or — if implemented as "compare vectors with matching ids" — silently ignore removed vectors. The manifest `counts` help only if the diff tool is specified to compare them. One sentence fixes this ("diff = set-equality of bundle paths + per-id set equality + byte equality per vector; any asymmetry fails"), but as written it is an implementer's choice inside the judge's core gate.

## F11 (MINOR) — D8 job YAML omits the steps D17 promises (mypy over `conformance/`, `conformance/tests`), and `conformance/tests` runs nowhere as specified; `just check` superset claim degrades

- D17.1: "the new conformance CI job runs `uv run mypy conformance/`"; D17.5: plugin/codec/diff unit tests under `conformance/tests/` are "run by the conformance CI job". D8's job spec (phase1-design.md:217-232) contains exactly two steps — corpus runner and drift check — neither of which collects `conformance/tests` (pytest arg is `conformance/runner`) or runs mypy. As written the promised unit tests and type gate execute nowhere; whoever fixes it by adding CI steps that `just check` doesn't run breaks the repo's documented "just check is a strict superset of CI" invariant (CLAUDE.md), which D8 explicitly claims to preserve. Verified justfile anchors: `check: lint fmt-check typecheck docstring-cov test-cov build` (justfile:12), `docstring-cov` = interrogate src/ + tests/ (justfile:134-136) — the D17.3 interrogate addition is fine, but the recipe/job matrix needs one consistent table.

## Attacks that FAILED (verified-OK claims)

- **Tautological replay in the core D7 architecture**: not confirmed as designed-in. `VectorTransport` serving canned responses while diffing live requests + live results is genuinely non-tautological for builder vectors (registry re-execution, one registry for recorder and runner) and for wire vectors IF F1 is fixed. The tautology risk is entirely concentrated in F1's unspecified capture path.
- **Worktree editable-resolution claim**: verified by recon transcript (test-infra-ci.md:70-72) — worktree `uv run` builds a worktree-local `.venv` resolving the worktree's `src/`; a `sed` marker was observed post-sync. The "silently tests the MAIN checkout" failure mode does not apply; the real problems are F3 (deps) and F4 (wrong commit).
- **D6 rule 4a scope**: matches R10.11's resolution exactly; the operand stringification site is real (`operand = str(value)`, segfilter.py:183; range ops `[str(v) for v in value]` at :181).
- **Sabotage anchors S1–S12**: all twelve file:line anchors spot-verified real and semantically as described (validation.py:116 `if prop.id <= 0`, validation.py:381 `fromisoformat`, api_client.py:2653 `_build_url("query", "/segmentation")`, api_client.py:153 region table, workspace.py:2139-2141 percentile mapping, pagination.py:287-288 cursor guard, segfilter.py:47 `"equals": "=="`, expressions.py:52 wrap, user_builders.py:248 `" and ".join`, live_query.py:137/:202 transforms, api_client.py:747 retry loop). S10/S11 are reachable through MockTransport-backed service tests (test_live_query.py:3 "Tests use httpx.MockTransport", funnel/retention classes at :287/:658) — the sites are on recordable paths, contingent on F1.
- **S12 catchability**: retry-exhaustion tests exist that do NOT patch `time.sleep` (test_api_client.py:485-501, `Retry-After: "0"`), so a `max_retries-1` sabotage yields a missing-interaction diff — provided F1/F7 are fixed.
- **D5 auth-pattern matching**: pattern-matching auth headers only for known test literals with loud abort on anything else is sound and not an over-normalization (credentials are fixed conftest literals, tests/conftest.py `make_session`).
- **D17 coverage-floor interaction**: correct — `test-cov` scopes `--cov=src/mixpanel_headless` (justfile:97-98, recon-verified), so conformance code cannot dilute or trip the 90% gate; packaging untouched since `conformance/` is outside `src/`.
