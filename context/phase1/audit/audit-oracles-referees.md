member is wire data). Error comparison is therefore code/class/path-based per
R5.4; the ok/error axis is part of the canonical string so return-vs-raise

## (d) Open-finding triage — deep-oracle REJECT of `build_frequency_filter_entry` payloads

**Payloads** (from `handoff.jsonl`, ids
`…test_frequency_filter_in_filter_section` / `…test_frequency_filter_mixed_with_filter`):
the library emits in `sections.filter[]`:

```json
{"behaviorType": "$frequency",
 "customProperty": {"behavior": {"aggregation": "total", "event": "Login",
                                 "filterOperator": "is at least", "filterValue": 5}},
 "resourceType": "people"}
```

(`build_frequency_filter_entry`, `src/mixpanel_headless/_internal/bookmark_builders.py:784-833` —
confirmed by reading the builder: `filterOperator`/`filterValue` live INSIDE
`customProperty.behavior`, and no top-level `filterType`/`filterOperator` are
emitted.)

**Validator** (`analytics/bookmark_parser/insights/validate.py`,
`insights_filter_section_validator` ~lines 240–285): each filter clause is a
`Schema({... "filterType": In(...), "filterOperator": str ...}, extra=ALLOW_EXTRA,
required=True)` — `filterType`/`filterOperator` are hard-required per clause
regardless of the harness's `require_all_keys=False` (that flag only loosens
the show-clause schemas). `behaviorType`/`customProperty` pass as ALLOW_EXTRA
extras; the REJECT is purely the two missing required keys. So the REJECT is
correctly produced — **not (iii), no harness routing error** (the payloads are
genuine insights payloads, correctly routed to the deep oracle).

**Would the SERVER truly reject? No — not today.** Decisive evidence from the
two live ingestion call sites (read-only):

1. Live query path — `analytics/api/version_2_0/insights/params.py:2946-2972`
   (`validate_insights_request_params`): wraps
   `validate_insights_bookmark_params_schema` in a try/except carrying the
   comment "TODO remove try-except once we're confident turning on required
   key validation didn't break anything". A `voluptuous.Invalid` whose message
   contains "required key not provided" AND whose path includes `show`, `time`
   or `filter` is NOT re-raised: it is reported to rollbar as
   "dry-run insights bookmark require keys" and the method returns False —
   and the caller (`from_params`, line 2896) ignores the return value and
   proceeds to execute the query.
2. Bookmark save path — `analytics/webapp/app_api/projects/bookmarks/views.py:909-945`
   and `:1116-1142`: the identical dry-run try/except (same TODO, same
   path-in-{show,time,filter} carve-out) around bookmark create/update.

The referee's exact error — `required key not provided @
data['sections']['filter'][N]['filterType']` — is squarely inside the
carved-out class at BOTH gates: today the server logs it and continues.

**Verdict: (ii), with a real residual risk — recorded, not dismissed.**
The deep voluptuous oracle applied strictly is stricter than what the live
server currently ENFORCES (required-key validation over show/time/filter
clauses is in dry-run/rollout mode at every call site). The structural
draft-04 referee correctly remains the binding referee for this clause type.
However this is NOT a clean "validator is stale" case:

- The validator encodes the shape Mixpanel intends to enforce (the TODOs say
  the try/except is temporary), and analytics' own insights-API fixture
  (`api/version_2_0/insights/test.py:4111`) shapes a native frequency filter
  clause with top-level `filterType`/`filterOperator`/`filterValue` and the
  `$frequency` marker under `behavior.behaviorType` — not the library's
  `customProperty`-nested form.
- If Mixpanel completes the rollout (removes the try/except), the library's
  shape starts failing validation at both the query and the save gate.

Per R10.7 this is a REPORTED potential latent Python-library issue (shape
divergence from the platform's native frequency-filter clause), not fixed
here. Recommended disposition (unchanged from the referee README, now with
call-site evidence): keep the escalation open, require the TS port to
replicate the Python shape byte-for-byte (R2.x bug-compatibility), and settle
it with a wire-level probe (does the query engine actually interpret the
`customProperty.behavior` form, or silently ignore the clause?) — semantics
downstream of the validation gate cannot be decided from static reading.

**Funnels dialect-routing fix — sound, not a masking hack.** Verified by
reading the schemas and the routing code:

- `analytics/bookmark_parser/funnels/schema/bookmark.json`: draft-04,
  `required: ["steps", "date_range"]`, `steps` = array of legacy flat
  `{bool_op, event, step_label}` objects, plus `allOf: [$ref
  common/schema/bookmark.json]`. It genuinely validates ONLY the legacy flat
  dialect; any modern sections-dialect funnel payload necessarily fails
  `'steps' is a required property` (the README's empirical 88/88 misroute
  rejection is consistent with the schema text).
- `harness.py` `structural_schema_for` routes to the funnels schema only when
  `bookmark_type == "funnels" and "steps" in params`; everything else goes to
  the common schema — which IS the funnels schema's own allOf-common layer,
  i.e. the exact subset of funnels-schema constraints that applies to
  non-legacy payloads. The funnels schema stays exercised via the
  `funnels-missing-steps` selftest control (re-verified REJECT above).
- Coverage honesty caveat: see finding F2 — the common schema is shallow for
  sections-dialect payloads, so "covered by the common schema route" is
  correct but weak (this is an asset limitation, not a routing error).

## Findings

**F1 (minor, artifact churn / nondeterminism) — deep-oracle REJECT message is
nondeterministic across runs.** Committed `last-run-deep.json` records
`required key not provided @ …['filterType']` for both REJECTs; my re-run
(identical pins, identical payloads) produced `…['filterOperator']`. Both keys
are missing from the same clause; voluptuous reports one of the equally-ranked
required-key errors nondeterministically. Verdicts (ACCEPT/REJECT), ids and
counts are identical, and D15b's comparison rule is explicitly verdict-level
("never message equality"), so nothing gates on the message — but anyone
regenerating the committed artifact will see spurious diffs, and any future
tooling that string-matches the error would be flaky. Recommend: normalize the
recorded error (e.g. sort/aggregate all missing keys, or record the path only)
before comparing/committing deep-run artifacts.

**F2 (minor, evidentiary weight) — structural 314/314 ACCEPT is weak evidence
for modern-dialect payloads, weakest for modern funnels.**
`common/schema/bookmark.json` declares no `required` and constrains only four
legacy top-level properties (`date_range`, `filter_by_event`,
`filter_by_cohort`, `group_by`); a modern sections-only payload matches it
near-vacuously (draft-04 permits unknown properties). All 314 corpus payloads
routed to this schema. For the 251 modern-nested insights-side payloads the
gap is substantially covered by the deep voluptuous oracle (125 insights
payloads validated) and by the TS 2020-12 InsightsBookmarkParams referee; but
the 88 modern-dialect funnel payloads get the near-vacuous common route AND
`SKIP_NON_INSIGHTS` from the deep oracle — i.e. their structural ACCEPT
asserts little beyond "is an object". This is an inherent limitation of the
available oracle assets (no draft-04 or generated schema exists for the modern
funnels dialect), the routing itself is correct, and the selftest controls
prove non-vacuity for what the schema does cover — but the gate summary
"314/314 ACCEPT" should be read with this caveat. Recommend: state it
explicitly in the referee README results section, and treat funnels-dialect
coverage as a Phase-2+ oracle gap (candidate: vendored funnels sections
contract, or wire-level probes).

**F3 (informational, triage record) — the open deep-oracle finding is
resolved as verdict (ii) with a live-rollout caveat** (full evidence in §(d)):
the server today tolerates the library's frequency-filter shape at both
ingestion gates (dry-run required-key validation), so the deep validator in
strict mode over-rejects relative to live enforcement; structural stays the
binding referee for this clause type. The escalation should REMAIN OPEN as a
future-compatibility risk: the validator's required keys match Mixpanel's own
fixtures and carry explicit intent to enforce ("TODO remove try-except…"), and
the library's `customProperty`-nested shape differs from the platform-native
clause. TS port must replicate the Python shape byte-for-byte until a
wire-level probe settles semantics (R2.x / R10.7).
